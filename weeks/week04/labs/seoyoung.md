## 문제

**1.** `~/lab` 아래에서 **1MB 미만** 파일을 찾으려고 `find ~/lab -size -1M`을 실행했는데 0바이트 파일만 나온다. 원인과 올바른 명령은?

**2.** `/etc` 아래에서 최근 30분 내에 수정된 **파일**을 찾아야 한다. 권한 문제와 에러 노이즈 없이.

**3.** `/var/log`에서 50MB 넘는 로그 중 "timeout"이 들어있는 파일명만 찾아야 한다. grep 단독으로는 왜 안 되는가?

**4.** 30일 넘은 로그들을 하나의 아카이브로 묶으려고 아래처럼 했는데 파일이 1개만 들어있다. 원인과 해결은?

```bash
find /var/log -name "*.log" -mtime +30 -exec tar -czvf old.tar.gz {} \;
```

**5.** `/var/lib/docker`가 디스크를 다 먹었다. 다른 디스크로 옮기면서 기존 경로는 그대로 쓰게 해야 한다. 하드 링크로는 왜 안 되는가?

**6.** 백업이라며 `ln data.txt data-backup.txt`를 만들어뒀다. 이게 백업 역할을 못 하는 이유는? (막아주는 것과 못 막는 것을 구분)

---

# 정답

**1.**`-size`는 비교 전에 크기를 **단위로 나눠 올림**하고, 그 다음엔 숫자만 비교한다.
1바이트만 있어도 `÷1M → 올림 → 1`이 되고 `1 < 1`이 거짓이 되므로, `-1M`은 사실상 0바이트만 통과시킨다.

```bash
find ~/lab -type f -size -1048576c
```

`c`(바이트)는 통 크기가 1이라 올림이 발생하지 않는다.
참고로 `+` 조건은 올림이 유리하게 작동해서 `+100M`처럼 큰 파일 찾기는 직관대로 동작한다.

---

**2.**

```bash
sudo find /etc -type f -mmin -30 2>/dev/null
```

- `mtime`은 일 단위라 너무 넓다 → 분 단위 `mmin`
- `type f` 없으면 디렉토리가 섞인다. 디렉토리 mtime은 "안에 파일이 추가·삭제된 시각"이라 노이즈가 많다
- **순서가 중요**: sudo로 권한을 먼저 확보하고, 남은 어쩔 수 없는 에러만 숨긴다. sudo 없이 `2>/dev/null`만 붙이면 "조용하지만 절반만 뒤진" 결과가 나온다

---

**3.**

```bash
sudo find /var/log -type f -size +50M -exec grep -l "timeout" {} + 2>/dev/null
```

grep은 **데이터 블록(내용)** 만 보고 크기·날짜·권한 같은 **inode의 메타정보**는 볼 수 없다.
반대로 find는 inode만 읽고 파일을 열지 않는다.

```
파일명 ──▶ inode ──▶ 데이터 블록
└─── find의 영역 ───┘   └ grep의 영역 ┘
```

그래서 find가 조건으로 후보를 좁히고(빠름), grep이 그 파일들만 열어본다(느린 작업 최소화).
`grep -l`은 파일명만 출력, `+`는 인자를 묶어 실행 횟수를 줄인다.

---

**4.**`\;`는 **파일당 한 번** 명령을 실행한다. tar가 매번 새로 생성되므로 앞의 것들이 덮어써지고 마지막 파일만 남는다.

```bash
# 방법 1 — 인자를 묶어서 1번 실행
find /var/log -name "*.log" -mtime +30 -exec tar -czvf old.tar.gz {} +

# 방법 2 — 목록을 stdin으로 전달
find /var/log -name "*.log" -mtime +30 | tar -czvf old.tar.gz -T -
```

- `T -`가 필요한 이유: tar는 기본적으로 stdin을 **"압축 해제할 아카이브 데이터"** 로 해석한다. `T -`가 "stdin을 파일 목록으로 읽어라"고 모드를 지정한다.

---

**5.**

```bash
mv /var/lib/docker /mnt/bigdisk/docker
ln -s /mnt/bigdisk/docker /var/lib/docker
```

하드 링크가 불가능한 이유는 **두 가지**다.

1. **파일시스템 경계** — 디렉토리 표에 적을 수 있는 건 inode 번호뿐이고, inode 번호는 그 파일시스템 내부에서만 유효하다. 다른 디스크의 같은 번호는 무관한 파일이다 (`Invalid cross-device link`)
2. **디렉토리 대상** — 순환 참조로 트리가 깨지므로 커널이 금지한다

심볼릭 링크는 **경로 문자열**을 담고, 경로에는 마운트 지점이 포함되므로 어디든 가리킬 수 있다.

---

**6.**
하드 링크는 사본이 아니라 **같은 파일**이다. 이름만 두 개일 뿐 inode와 데이터 블록을 공유한다.

|  | 하드 링크가 |
| --- | --- |
| 원본 **삭제** | 막아준다 (카운트가 0이 아니므로 데이터 유지) |
| 원본 **수정** | **막지 못한다** (같은 파일이므로 양쪽에 반영) |

```bash
echo "원본" > data.txt
ln data.txt data-backup.txt
echo "실수로 덮어씀" > data.txt
cat data-backup.txt        # "실수로 덮어씀" ← 백업도 같이 바뀜
ls -li data.txt data-backup.txt   # 같은 inode
```

백업의 목적이 보통 "실수로 수정·삭제한 것 복구"이므로, 절반만 막아주는 건 백업이 아니다. → `cp`를 쓴다.

## 요약
| 문제 | 핵심 |
| --- | --- |
| 1 | `-size`는 올림 후 숫자 비교 → 미만 조건엔 `c` |
| 2 | `-type f` + sudo 먼저, 노이즈 숨김은 나중 |
| 3 | find는 inode(속성), grep은 데이터 블록(내용) |
| 4 | `\;`는 파일당 실행 → `+` 또는 `-T -` |
| 5 | 하드 링크는 inode 번호를, 심볼릭은 경로를 가리킨다 |
| 6 | 하드 링크는 사본이 아니다 |
