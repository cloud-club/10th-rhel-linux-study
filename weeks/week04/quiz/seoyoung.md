# 정답

**1. ③ `tar -cvf backup.tar.gz dir/`**

`z`가 없으므로 압축되지 않는다. 확장자만 `.gz`인, 압축 안 된 tar 파일이 만들어진다.

**아카이브(묶기)와 압축(줄이기)은 다른 일**이고, tar는 묶기만 한다. `z`/`j`/`J`가 gzip/bzip2/xz를 호출하는 옵션이다.

②가 동작하는 이유: 풀 때는 tar가 **헤더를 보고 형식을 자동 감지**한다. 묶을 때는 어떤 형식으로 만들지 알 수 없으므로 자동 감지가 불가능하다.
→ **`c`에는 z/j/J 필수, `x`에는 선택.**

참고로 `f`는 바로 다음 인자를 파일명으로 읽으므로 **항상 마지막**에 와야 한다. `tar -cfv backup.tar dir/`은 `v`라는 이름의 파일을 만들려 한다.

---

**2. ② 0바이트 파일만**

- `size`는 비교 전에 크기를 **단위로 나눠 올림**하고, 그 다음에는 단위를 보지 않고 숫자만 비교한다.

| 크기 | ÷ 1M | 올림 | `1 <` 판정 |
| --- | --- | --- | --- |
| 0B | 0 | 0 | 참 |
| 1B | 0.0000009 | **1** | 거짓 |
| 4096B (디렉토리) | 0.0039 | **1** | 거짓 |

1바이트만 있어도 1M으로 취급되므로 올림값이 0인 것, 즉 0바이트만 통과한다.
의도한 "1MB 미만"은 올림이 없는 바이트 단위로 써야 한다. → `-size -1048576c`

참고로 `+` 조건은 올림이 유리하게 작동해 `+100M` 같은 큰 파일 찾기는 직관대로 동작한다.

---

**3. ③ 50MB를 넘는 파일 중에서 특정 문자열 검색**

grep은 **데이터 블록(내용)** 만 보고, 크기·날짜·권한 같은 **inode의 메타정보**는 볼 수 없다.

```
파일명 ──▶ inode ──▶ 데이터 블록
└─── find의 영역 ───┘   └ grep의 영역 ┘
```

①은 `--include="*.conf"`, ②는 `-I`, ④는 `-C 3`으로 가능하다.
③은 find가 조건으로 후보를 좁히고 grep이 그 파일만 열어봐야 한다.

```bash
find /var/log -type f -size +50M -exec grep -l "패턴" {} + 2>/dev/null
```

---

**4. ② 심볼릭 링크만 새 파일을 가리키고, 하드 링크는 원래 데이터를 유지한다**

- **심볼릭 링크**는 데이터 블록에 **경로 문자열**을 담고 있다. 확인하는 것은 "그 경로에 뭔가 있나"뿐이고 내용이 뭐든 따라간다. → 원본 데이터는 영구히 사라졌는데 링크는 정상 동작하므로, 조용히 엉뚱한 파일을 읽는 위험이 있다.
- **하드 링크**는 **inode 번호**를 가리킨다. 원본 삭제 시 링크 카운트가 1 줄어들 뿐(0이 아니므로 데이터 유지)이고, 같은 이름의 새 파일은 **다른 inode**라서 무관하다.

깨진 링크의 실패 원인이 데이터 해제가 아니라 **경로 해석 실패**라는 것이 이 실험에서 드러난다.
